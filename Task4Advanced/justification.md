# Задание 4. Обоснование событийного подхода

Почему целевая платформа строится на доменных событиях (Kafka + Schema Registry + DLQ, Data Mesh), а не на Camel ESB и «логике в DWH». Связано с [`bounded-contexts.md`](bounded-contexts.md:1), [`events.md`](events.md:1) и стадиями Task3.

## Преимущества событийной архитектуры
- **Слабая связанность:** обмен фактами, продюсер не знает подписчиков — нет «узкого горла» и каскадных отказов.
- **Независимое масштабирование:** домены деплоятся/версионируются отдельно; партиции по ключу агрегата дают горизонтальный рост.
- **Near-real-time:** потоки (Flink) наполняют витрины — отчёты за секунды вместо часов.
- **Устойчивость:** очереди сглаживают пики; ретраи + **DLQ** — без потерь.
- **Быстрый TTM и онбординг:** новый потребитель просто подписывается на топик; новое направление (Фарма/Медтехника) = новый домен + топики + схемы.
- **Эволюция схем:** **Schema Registry** (BACKWARD) меняет контракты, не ломая подписчиков.
- **Приватность:** медданные не попадают в аналитический контур.

## Почему Camel ESB и «логика в DWH» тормозят
- Синхронные point-to-point → жёсткие зависимости, отказ одного ломает остальных.
- Логика/трансформации в DWH → единая точка изменений, полная регрессия на любую доработку.
- Сотни ТБ в батче → отчёты часами, near-real-time невозможен.
- Отказ шины/DWH останавливает интеграции; новое направление требует правок ядра — медленный TTM.

## Сравнительная таблица

| Аспект | Camel/DWH сейчас (AS-IS) | Событийная архитектура (целевое) |
| --- | --- | --- |
| Связность | Синхронные point-to-point | Публикация/подписка |
| Изменения | Единая точка в DWH, регрессия | Локально в домене |
| Масштабирование | Вертикальное, общий DWH | Горизонтальное, партиции |
| Задержка отчётов | Часы (batch) | Секунды (Flink) |
| Устойчивость | Отказ = остановка | Очереди + ретраи + DLQ |
| Онбординг направления | Правки шины и DWH | Новый домен: топики + схемы |
| Эволюция контрактов | Ручная, ломающая | Schema Registry, BACKWARD |
| Логика / приватность | Монолит DWH, всё внутри | В агрегатах; медданные вне аналитики |

## Стадии и роль ACL-мостов

| Стадия | Горизонт | Событийная архитектура | Camel/DWH и ACL |
| --- | --- | --- | --- |
| 1 | 0–6 мес | Пилот 1–2 домена; DLQ, Schema Registry | Основные источники через CDC/Debezium |
| 2 | 6–18 мес | Критические домены, потоковые витрины | Демотированы до **ACL-мостов** |
| 3 | 18–36 мес | Отказ от синхронных point-to-point | **Выведены** из эксплуатации |

**ACL-мосты** временно изолируют доменные модели от legacy и транслируют изменения в нормализованные события; снимаются по мере миграции (критерии — в [`../Task3Advanced/01-c4-target-architecture.md`](../Task3Advanced/01-c4-target-architecture.md:73)).

**Вывод:** слабая связность и Data Mesh дают независимую эволюцию доменов, потоки — near-real-time, Schema Registry/DLQ — управляемость и устойчивость; Camel и DWH остаются лишь временными ACL-мостами до стадии 3.
